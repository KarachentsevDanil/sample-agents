# Task t13: Reschedule follow-up (date calculation error)

## Failure Summary

**Task**: "Nordlicht Health asked to reconnect in two weeks. Reschedule the follow-up accordingly and keep the diff focused."
**Expected**: `next_follow_up_on = "2026-10-25"` (VM time 2026-10-11 + 14 days)
**Actual**: `next_follow_up_on = "2026-10-17"` (old follow-up 2026-10-03 + 14 days)
**Score**: 0.0

The agent interpreted "reconnect in two weeks" as "add 14 days to the existing follow-up date" instead of "add 14 days to today (VM time)." This is a **100% consistent failure** across 6 consecutive trials, always off by exactly 8 days (the gap between the old follow-up date and VM time). One prior trial using the Codex API backend scored 1.0 by correctly using VM time as the anchor.

## Root Cause Analysis

### Context Builder Phase

The context builder **does** fetch VM time correctly via `_fetch_vm_time()` in `context.py:110-116`. It stores the result in `ctx.vm_time`. The `build_initial_user_message()` function in `prompts.py:21-23` then injects it as:

```
# CURRENT TIME
<vm_time_value>
```

**Verdict**: VM time is fetched and included in the ReAct prompt. The infrastructure works correctly.

### Planner Phase

The planning stage (`planning.py:74-90`, `_build_planning_input`) assembles its input from:
- `ctx.task`
- `ctx.agents_md`
- `ctx.preloaded_context_files`
- `ctx.dfs_tree`
- `ctx.past_mistakes`

**Critical gap**: `ctx.vm_time` is **never included** in the planning input. The planner has no awareness of VM time. This means the planner cannot generate a step like "use CURRENT TIME (2026-10-11) as the reference date for 'two weeks'." Instead, the plan's `task_interpretation` likely says something generic like "add two weeks to the follow-up date," which the ReAct agent then interprets as adding 14 days to the existing field value.

### ReAct Phase

The ReAct loop receives VM time under `# CURRENT TIME` in its context (confirmed by `prompts.py:22-23`). However:

1. The agent jumped directly to search -> read -> write without pausing to reason about which date to anchor "two weeks" from.
2. There is no reasoning text logged in `react_trace.jsonl` -- the agent went straight to tool calls in every step.
3. The execution plan (from the planner, which had no VM time) likely instructed: "read the current follow-up date, add 14 days, write it back."
4. The `# CURRENT TIME` header is a passive context section. It does not call out that relative date expressions ("in two weeks", "next month") must be anchored to this time. A nano model under a tight step budget follows the plan mechanically and ignores ambient context that the plan does not reference.

**Evidence from errors.jsonl**: Across 6 failed trials with varying VM times and follow-up dates, the error is always exactly `expected - got = 8 days`, and the agent always computes `old_follow_up + 14`. This proves the agent never once consulted VM time.

**Evidence from retrospective.json**: The one successful trial (`vm-02knyw1fqmn3ogl`, score 1.0, different backend/run) explicitly noted: "VM context time (2026-04-16) correctly identified as reference for 'two weeks from now' = 2026-04-30." That run had a different pipeline configuration that made the time more salient.

### Primary Root Cause

**The planner does not receive VM time, so it cannot generate a plan that anchors relative dates to "today."** The ReAct agent receives VM time passively in context but follows the planner's instructions, which implicitly anchor to the existing field value. The `# CURRENT TIME` section is not prominent or directive enough for a nano model to override the plan's implicit anchoring.

This is a two-layer failure:
1. **Planning layer** (primary): VM time absent from planning input, so the plan cannot specify the correct anchor.
2. **Prompt layer** (secondary): Even in the ReAct prompt, `# CURRENT TIME` is a bare header with no guidance on when/how to use it for relative date expressions.

## Suggestions (generalizable, not task-specific)

### S1: Include VM time in the planning stage input

- **What**: Add `ctx.vm_time` to `_build_planning_input()` in `planning.py`, formatted as `Current VM time: {ctx.vm_time}`.
- **Where**: `agent_pipeline_openai/stages/planning.py`, method `_build_planning_input`, around line 75.
- **Why**: The planner needs to know "today's date" to correctly interpret any task with relative time expressions ("in two weeks", "next month", "by end of quarter"). Without it, the plan will always default to anchoring off existing data rather than the current date.
- **Scope**: Affects all tasks with relative date/time references (t13 and any similar scheduling/rescheduling tasks).
- **Confidence**: HIGH. The retrospective from the successful run confirms that correct anchoring to VM time was the differentiator.

### S2: Add a directive annotation to the CURRENT TIME context section

- **What**: Change the `# CURRENT TIME` section in `build_initial_user_message()` from a bare value to an annotated directive:
  ```
  # CURRENT TIME (use as "today" for all relative date calculations)
  {vm_time}
  When the task says "in X days/weeks/months", calculate from THIS date, not from existing field values.
  ```
- **Where**: `agent_pipeline_openai/prompt_resources/prompts.py`, line 23.
- **Why**: Nano models under step budgets follow instructions literally. A passive data header is easily ignored when the plan says "add two weeks to the follow-up." An explicit directive makes the anchor unambiguous. This is a known pattern: LLMs anchor to the most salient number they encounter -- the field value they just read -- unless explicitly told otherwise.
- **Scope**: All tasks involving relative date arithmetic.
- **Confidence**: MEDIUM-HIGH. The successful Codex run used a different prompt configuration that made VM time more salient. This replicates that effect.

### S3: Add a planning prompt rule for temporal reference resolution

- **What**: Add a rule to the planning prompt (`planning/v2.yaml`) under `## Planning rules`:
  ```
  - When the task involves relative time expressions (e.g., "in two weeks", "next month",
    "by Friday"), the plan MUST include a step that explicitly states the anchor date
    (VM current time) and computes the target date before any file writes.
  ```
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/planning/v2.yaml`, after the existing planning rules.
- **Why**: Even with VM time available, the planner may not spontaneously use it correctly. An explicit rule ensures the plan always includes a "compute target date" step for temporal tasks, making the reasoning chain auditable and the ReAct agent's behavior deterministic.
- **Scope**: All temporal/scheduling tasks.
- **Confidence**: MEDIUM. Depends on S1 being implemented first (planner must have the date to reference it).

### S4: Add past-mistake feedback that specifically calls out the anchor-date error pattern

- **What**: Update the errors.jsonl for t13 to include a `failure_category` of `"date_anchor_error"` and a more explicit reason string like: `"Used old field date as anchor instead of VM time. 'In two weeks' means today + 14 days, not old_date + 14 days."` Ensure the past-mistakes injection in `build_initial_user_message` surfaces this clearly.
- **Where**: `mistakes/t13/errors.jsonl` (data), and verify `prompts.py:43-53` formats it readably.
- **Why**: The pipeline already supports past-mistake injection, but the current error messages are generic (`"JSON mismatch in 'accounts/acct_001.json': next_follow_up_on: expected..."`). A category and corrective instruction give the model a clear behavioral correction rather than just a diff.
- **Scope**: This specific error pattern, but the `failure_category` taxonomy benefits all tasks.
- **Confidence**: MEDIUM. Past-mistake injection helps but is a secondary defense -- the primary fix is S1+S2.

## Tool Recommendations

No new tools are needed. The existing `_fetch_vm_time()` infrastructure works correctly. The issue is purely in how the fetched time is distributed to downstream stages and how prominently it appears in prompts.

## Rule Recommendations

- **AGENTS.md**: No changes needed. The AGENTS.md already correctly says "When rescheduling follow-up work, update both the reminder and the owning account if both records carry the date" -- the agent followed this rule. The missing rule is about *temporal anchoring*, which belongs in the pipeline prompts, not in per-VM authority files.

- **System prompt (v13.yaml)**: Consider adding under SCOPE or a new DATE HANDLING section:
  ```
  DATE HANDLING:
  - "Today" is the CURRENT TIME shown in your context. All relative date expressions
    ("in two weeks", "next month", "by Friday") are relative to CURRENT TIME.
  - Never use an existing field value as the anchor for relative dates unless the task
    explicitly says "from the current date" or "from the existing follow-up."
  ```

## Pipeline / Pre-loading Recommendations

1. **Highest priority**: Inject `ctx.vm_time` into `_build_planning_input()` (S1). This is a one-line fix that addresses the root cause.

2. **Second priority**: Make `# CURRENT TIME` directive in the ReAct prompt (S2). This is also a small change with high impact.

3. **Third priority**: Add the planning rule for temporal tasks (S3). This adds robustness for edge cases where even with the date available, the planner might not use it.

4. The planning stage is the critical chokepoint. Since the plan drives the ReAct agent's behavior, any information the planner lacks will be effectively invisible to the execution, even if it appears elsewhere in the context. This principle applies beyond dates -- any task-critical metadata (user timezone, currency, locale) should flow through the planner.
