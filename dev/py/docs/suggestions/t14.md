# Task t14: Send email (outbox mechanism not recognized)

## Failure Summary

The agent was asked to send an email to Blue Harbor Bank. It correctly discovered the `outbox/` mechanism by reading `outbox/README.MD` and `outbox/seq.json`, found the correct account (`acct_004`) and contact (`cont_004` with email `esmee.gerritsen@blue-harbor-bank.example.com`), and even verified the next sequence number (84592). However, it never wrote the email file. Instead, at step 8, it called `done()` with `OUTCOME_NONE_UNSUPPORTED`, stating: "I could not complete the email because this task requires creating outbox files, but the available step budget warning requires I stop before writing."

This is the **third** failure on this task across runs. Historical errors show: (1) no answer produced, (2) wrong email address used, (3) this run -- declared unsupported despite having discovered the mechanism.

## Root Cause Analysis

### Context Builder Phase

The context agent **worked correctly**. It discovered and read 12 files including:
- `AGENTS.MD` -- which explicitly states: "emails - outgoing emails are sent by writing them to `outbox`" and "Send outbound emails by writing them to `outbox`; do not invent external CRM sync features"
- `outbox/README.MD` -- which documents the exact JSON format, seq.json protocol, and invariants

The outbox mechanism was fully loaded into the agent's context. **No failure here.**

### Planner Phase

The planner assessed the task as **medium complexity with 4 steps**. This produced a step budget of `4 * 2 + 2 = 10` steps.

The planner had access to both AGENTS.MD (which says "send by writing to outbox") and the system prompt v13 (which says "NOT AVAILABLE: sending email"). The plan created 4 steps, which should have been sufficient. However, the plan was created in tension between two contradictory instructions:
- AGENTS.MD (authority file): "outgoing emails are sent by writing them to `outbox`"
- System prompt v13: "NOT AVAILABLE: sending email" and "If a task requires something NOT AVAILABLE, use OUTCOME_NONE_UNSUPPORTED immediately. Do NOT draft content, create placeholder files, or return OUTCOME_OK."

The planner may have hedged by creating a plan that explores the mechanism without committing to using it.

### ReAct Phase

Step-by-step trace:
1. **Step 1**: Searched for "Blue Harbor Bank" in accounts -- found `acct_004.json`
2. **Step 2**: Searched for "Blue Harbor" in contacts -- no results (contact doesn't contain "Blue Harbor" in its text)
3. **Step 3**: Read `outbox/seq.json` -- got `{"id": 84592}`
4. **Step 4**: Read `outbox/README.MD` -- got full outbox protocol documentation
5. **Step 5**: Read `accounts/acct_004.json` -- got account with `primary_contact_id: cont_004`
6. **Step 6**: Read `contacts/cont_004.json` -- got email `esmee.gerritsen@blue-harbor-bank.example.com`
7. **Step 7**: Read `outbox/84592.json` -- got `NOT_FOUND` (confirming the slot is free). **Budget warning injected at this step** (step 7 >= 10-3).
8. **Step 8**: Called `done()` with `OUTCOME_NONE_UNSUPPORTED` instead of writing the email

The agent had all the information needed. It was 2 tool calls away from completion (write email JSON, update seq.json). The decision to return UNSUPPORTED was driven by the confluence of two factors:

1. **The system prompt's explicit prohibition**: v13 says "NOT AVAILABLE: sending email" with a hard instruction to "use OUTCOME_NONE_UNSUPPORTED immediately" and "Do NOT draft content, create placeholder files." The agent interpreted writing an outbox JSON file as "drafting content" or "creating a placeholder file" -- exactly what the system prompt forbids.

2. **Step budget pressure**: The budget warning at step 7 said "You MUST call done() on your NEXT action." The agent had 2 more writes to do but was told it must call done() immediately. Even if the agent wanted to write the email, the budget warning forced premature termination.

### Primary Root Cause

**Dual root cause:**

1. **System prompt contradiction with authority files (PRIMARY)**: The v13 system prompt's "NOT AVAILABLE: sending email" blanket rule directly contradicts AGENTS.MD's "outgoing emails are sent by writing them to `outbox`." The system prompt tells the agent that email is unsupported AND explicitly instructs it not to create files as a workaround ("Do NOT draft content, create placeholder files"). The agent read both outbox/README.MD and AGENTS.MD but was unable to reconcile the system prompt prohibition against the file-based email mechanism documented in the workspace authority files. The system prompt won because it is framed as a hard constraint with an explicit example: `"Email Sam a digest" -> OUTCOME_NONE_UNSUPPORTED`.

2. **Tight step budget with budget warning causing premature abort (CONTRIBUTING)**: The 4-step plan produced a budget of 10. The agent consumed 7 steps on reads (6 were necessary, 1 was exploratory), leaving only 3 steps. The budget warning fired at step 7, demanding immediate done(). The agent needed at least 2 more tool calls (write email file + update seq.json). Even if the agent wanted to write the email, the budget warning coerced it into terminating.

## Suggestions (generalizable, not task-specific)

### S1: System prompt must distinguish between external network capabilities and file-based domain operations

- **What**: Rewrite the "NOT AVAILABLE" section in the system prompt to clarify that the prohibition applies to external network/API operations, not to file-based workflows that simulate those operations within the filesystem. Add a positive qualifier: "Writing files to designated directories (e.g., outbox/) IS a file operation, not a network operation, even when the file represents an email or message."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/system/v13.yaml` -- the CAPABILITIES section
- **Why**: The current phrasing "NOT AVAILABLE: sending email" is overly broad. The agent has `write_file` capability and the workspace has an outbox mechanism. "Sending email" via SMTP is not available, but "writing an email JSON to outbox/" is a file write -- a fully available capability. The prompt's example ("Email Sam a digest" -> OUTCOME_NONE_UNSUPPORTED) reinforces the wrong behavior for this entire class of tasks.
- **Scope**: Affects any task where a domain action (email, notification, calendar) is implemented as a file-system convention rather than an external API. This likely affects multiple tasks.
- **Confidence**: 95% -- This is the unambiguous primary cause. The agent read the outbox docs, found the contact email, confirmed the seq number, and still refused because the system prompt explicitly prohibited "sending email."

### S2: Authority files (AGENTS.MD) should override system prompt on domain-specific capability questions

- **What**: Add a meta-rule to the system prompt that establishes priority: "If AGENTS.md or trusted rule files describe a file-based mechanism for performing an action (e.g., outbox/ for emails), that mechanism IS available. The NOT AVAILABLE list refers only to capabilities requiring external network access or APIs not present in the filesystem."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/system/v13.yaml` -- add between CAPABILITIES and AUTHORITY sections
- **Why**: The current AUTHORITY section says "AGENTS.md and files listed under [TRUSTED RULE] are your instructions" but does not clarify that AGENTS.md can effectively expand the capability set when it describes file-based workflows. The agent could not reconcile the two sources.
- **Scope**: General architectural improvement. Any time a workspace defines a file-based convention for a "network-sounding" operation, the agent needs to know the convention is authoritative.
- **Confidence**: 90%

### S3: Step budget formula should account for write-heavy tasks requiring multiple file mutations

- **What**: The budget formula `plan_steps * 2 + 2` is too tight for tasks that involve (a) lookup/discovery reads AND (b) multi-file writes. For a 4-step plan, budget = 10, but this task needed ~9 steps (6 reads + 2 writes + 1 done). Consider either: increasing the multiplier to `plan_steps * 2.5 + 3`, or having the planner explicitly flag "write-heavy" tasks for a budget bonus.
- **Where**: `agent_pipeline_openai/models.py` -- `budget_from_plan()` function
- **Why**: The budget warning fires at `max - 3`, meaning effective working steps = budget - 3. For budget=10, that is 7 working steps before the warning coerces termination. This task needed 8 working steps. The agent was forced to choose between ignoring the budget warning (risky) and completing the task (correct).
- **Scope**: Affects any medium-complexity task that combines reads with writes. Tasks that create files after lookups are common (email, invoice, reminder creation).
- **Confidence**: 75% -- This was the contributing cause. Fixing S1 alone might be sufficient since the agent could have written the email earlier instead of reading `outbox/84592.json` to check if it existed.

### S4: Budget warning language should not force premature termination when the agent is mid-task

- **What**: Change the budget warning from "You MUST call done() on your NEXT action" to "You are approaching your step limit. Prioritize completing the most critical remaining action (especially file writes), then call done()." Allow 1-2 more tool calls after the warning instead of demanding immediate termination.
- **Where**: `agent_pipeline_openai/stages/react_tools.py` -- `_STEP_BUDGET_WARNING` constant, and the trigger threshold (`max_steps - 3` could become `max_steps - 2`)
- **Why**: The current warning creates a cliff: the agent must immediately abandon its work and report. If the agent is 1-2 writes away from completion, it should finish rather than report failure. A "soft landing" that allows critical writes would prevent cases where the agent does all the research but never commits the result.
- **Scope**: General improvement. Any task where the agent front-loads reads and back-loads writes is vulnerable to this pattern.
- **Confidence**: 80%

### S5: The planner should front-load write operations when the task's primary deliverable is a file creation

- **What**: Add a planning heuristic or instruction: "When the task's primary deliverable is creating one or more files (e.g., drafting an email, creating a reminder), plan the write steps early. Do lookups only for information strictly required before writing, and defer optional verification reads to after the write."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/planning/v2.yaml` -- add to "Planning rules" section
- **Why**: In this trace, the agent read 6 files before attempting any write. Steps 3-4 (reading outbox/seq.json and README.MD) were correct early reads, but step 7 (checking if 84592.json exists) was a discretionary verification that consumed a budget slot. If the write had come before the verification read, the task would have succeeded.
- **Scope**: General planning improvement for create/write tasks.
- **Confidence**: 65% -- Helps with budget pressure but does not fix the root capability mismatch.

## Tool Recommendations

No new tools needed. The agent has `write_file` which is sufficient for the outbox mechanism. The issue is purely in prompt-level instructions preventing the agent from using its existing tools.

## Rule Recommendations

1. **Refine "NOT AVAILABLE" to "NOT AVAILABLE (external/network)"**: The system prompt's capability list should be scoped to external operations. File-based simulation of domain operations (outbox for email, files for calendar entries, etc.) are file operations, not external capabilities.

2. **Add a reconciliation rule**: When AGENTS.MD describes a file-based mechanism for an action that appears in the "NOT AVAILABLE" list, the AGENTS.MD mechanism takes precedence because it is a file operation, not a network operation.

3. **Past-mistake injection should include corrective guidance, not just the error**: The errors.jsonl for this task includes a prior failure with the same OUTCOME_NONE_UNSUPPORTED pattern. When past mistakes are injected, they should include a hint like "The outbox mechanism IS a file operation, not email sending" so the agent does not repeat the same misinterpretation.

## Pipeline / Pre-loading Recommendations

1. **Pre-classify task type in the planner**: The planner could tag tasks as "file-creation" vs "file-read" vs "file-mutation." File-creation tasks should get a write-oriented budget and the planner should flag that the deliverable is a new file, not a read.

2. **Context builder already loads outbox/README.MD correctly**: No changes needed to context discovery. The mechanism was fully discoverable.

3. **Consider a "capability reconciliation" micro-step** between planning and execution: After the plan is built, a lightweight check could compare the plan's tool requirements against both the system prompt's capability list AND the authority files' described mechanisms. If a plan step uses `write_file` to implement something the system prompt calls "NOT AVAILABLE," inject a clarification note that this is a file operation, not an external capability.
