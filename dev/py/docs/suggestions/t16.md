# Task t16: Email lookup for "Voigt Elisabeth"

## Failure Summary

The task asked: "What is the email address of Voigt Elisabeth? Return only the email".
Expected answer: `lena.wagner@greengrid-energy.example.com` (score 0.0).

The agent returned a descriptive sentence instead of the raw email address:
> "Identified the contact record for Wagner Lena as contacts/cont_005.json and extracted the stored email field."

There are **two independent failures** here:

1. **Answer format**: The agent returned a narrative description instead of the bare email string. The task explicitly said "Return only the email", but the `done()` message contains zero email text.
2. **Stale past-mistakes context vs randomized benchmark data**: The benchmark randomizes contact names and data per trial. The task instruction the agent actually received was "What is the email address of **Wagner Lena**?" (a different trial's randomization), and the agent correctly found Lena Wagner in cont_005.json. However, the benchmark scored against trial vm-02krddnnfrrpcxl's expected answer which is `lena.wagner@greengrid-energy.example.com`. The agent's message mentions finding the right person but never outputs the actual email string.

The **primary scoring failure** is answer format: even though the agent found the correct contact, it did not include the email address in its `done()` message. The benchmark evaluator string-matches the answer against the expected email.

## Root Cause Analysis

### Context Builder Phase

The context builder discovered 12 files including all README.MD files and AGENTS.md. It correctly identified the contacts and accounts data model. However, it did not pre-load any contact data files -- it only loaded structural/rule files (READMEs, docs). This is appropriate behavior since the context agent's purpose is rule discovery, not data pre-loading.

No issues in this phase.

### Planner Phase

The planning stage received the task and produced a "simple" plan with 3 steps. The planning input fragment shows:
```
Task: What is the email address of Wagner Lena? Return only the email
```

The planner correctly identified this as a contact lookup task. The plan was reasonable: search contacts, find the person, extract the email. No issues in the plan itself.

### ReAct Phase

The ReAct loop executed 13 steps across 3 LLM turns:

1. **Step 1**: `search("Wagner Lena", root="contacts")` -- returned empty `{}`. The search tool searches file contents, and "Wagner Lena" (reversed format) did not match the stored `full_name: "Lena Wagner"`.
2. **Steps 2-12**: After search failed, the agent fell back to listing the contacts directory and then reading ALL 10 contact files sequentially. It successfully found cont_005.json containing "Lena Wagner".
3. **Step 13**: Called `done()` with message "Identified the contact record for Wagner Lena as contacts/cont_005.json and extracted the stored email field." -- a description, NOT the email address.

**Critical failure**: The `done()` message is a narrative summary. The benchmark evaluator compares the `done()` message against the expected answer string `lena.wagner@greengrid-energy.example.com`. Since the message contains no email, score = 0.

### Primary Root Cause

**The agent does not include the actual data value (the email address) in its `done()` message when the task asks for a specific piece of data.** The model treats `done()` as a "what did I do" summary rather than a "here is the answer" response.

This is a **prompt/instruction gap**: the system prompt and the `done()` tool description say "What you did or why you can't. Be specific." -- this encourages the model to describe its actions rather than return the requested data value. For data-retrieval tasks ("What is X? Return only X"), the answer must BE the data, not a description of finding it.

### Secondary Issue: Reversed Name Search

The task uses reversed name format "Voigt Elisabeth" (family-name given-name). The agent's initial search for "Wagner Lena" returned empty because the search tool does literal substring matching against file contents where the stored format is "Lena Wagner" (given-name family-name). This forced a brute-force scan of all contact files. While the fallback worked, it consumed 12 of 13 steps and would be inefficient for larger datasets.

### Error History Pattern

The errors.jsonl shows **6 consecutive failures** on t16-type tasks across different trials. All share the same pattern: the `agent_answer` field contains a description rather than the actual data value. Examples:
- "Extracted the email from contacts/cont_006.json."
- "Found the matching contact record for Dennis Bender and extracted the email address."
- "Found matching contact and extracted email from contacts/cont_004.json."

This is a systemic problem: the agent never returns raw data values for lookup queries.

## Suggestions (generalizable, not task-specific)

### S1: Instruct `done()` to include the answer value, not just a description

- **What**: Modify the `done()` tool description and the system prompt to explicitly instruct the model that for data-retrieval tasks, the `message` field must contain the actual requested data value. Add guidance like: "If the task asks 'What is X?' or 'Return only X', your message MUST contain the literal value of X, not a description of where you found it."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/system/v13.yaml` (COMPLETION section) and `agent_pipeline_openai/stages/react_tools.py` (done tool schema description, line ~499).
- **Why**: The benchmark evaluator string-matches the done() message against the expected answer. A narrative description will never match a data value. This is the root cause of 100% of t16 failures and likely affects all data-retrieval tasks.
- **Scope**: All lookup/query tasks (email, phone, address, ID, date lookups). Likely 30-40% of benchmark tasks.
- **Confidence**: 95% -- this is a clear prompt gap. The model follows its instructions to describe "what you did" rather than outputting the answer.

### S2: Handle reversed name formats in search queries

- **What**: Add a prompt instruction or search pre-processing step that when searching for a person by name, the agent should try both the original query format AND a word-reversed version. For "Voigt Elisabeth", also try "Elisabeth Voigt". This can be a prompt-level instruction ("When searching for a person's name, also try reversing first/last name order") or a search wrapper that automatically issues both queries.
- **Where**: System prompt search guidance section, or as a wrapper in `react_tools.py` `search()` function.
- **Why**: The benchmark uses "Surname Givenname" format in task instructions, but the CRM stores "Givenname Surname". A single failed search wastes a step and forces brute-force file enumeration.
- **Scope**: All person-name lookup tasks. Reduces step count from ~12 to ~2 for contact lookups.
- **Confidence**: 80% -- the search would match if either word order is tried.

### S3: Add explicit "return format" instructions to the system prompt

- **What**: Add a rule to the system prompt: "When the task says 'Return only X' or asks a question expecting a specific value, your done() message must be ONLY that value -- no preamble, no explanation, no file references. Example: if asked 'What is the email of X? Return only the email', your done() message should be exactly 'user@example.com'."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/system/v13.yaml` (add under COMPLETION section).
- **Why**: The phrase "Return only the email" is a strong signal from the benchmark that the answer must be a bare value. The model currently ignores this signal.
- **Scope**: All "return only" style tasks across the benchmark.
- **Confidence**: 90%.

### S4: Search by individual name components, not full string

- **What**: When the search tool returns empty for a multi-word name query, the agent should decompose the name into individual words and search for each separately (e.g., search "Voigt" then search "Elisabeth"). This narrows results faster than brute-force file reading.
- **Where**: Prompt instructions for the search strategy, or as planning-stage guidance.
- **Why**: The search tool does substring matching. Searching for "Voigt" alone would immediately find the contact file containing "Elisabeth Voigt", even if the full reversed name fails.
- **Scope**: Any multi-word entity lookup (person names, company names, etc.).
- **Confidence**: 75%.

## Tool Recommendations

1. **Modify `done()` tool description** (react_tools.py line 499): Change from "What you did or why you can't. Be specific." to "The answer to the task. If the task asks for a specific value (email, name, date, etc.), this MUST be that value. If the task asks 'Return only X', this must be ONLY X. Otherwise, describe what you did."

2. **Consider adding a `search_contact()` convenience tool** that searches contacts by any name component (first, last, full, reversed) and returns matching records. This would reduce the step count for the most common task type.

## Rule Recommendations

1. **Add answer-format awareness**: The system prompt should distinguish between "action tasks" (create/update/delete files) and "query tasks" (look up and return a value). For query tasks, the done() message IS the answer.

2. **Add name-normalization guidance**: "When searching for a person, try multiple name orderings: the name as given, the name with words reversed, and individual name components."

## Pipeline / Pre-loading Recommendations

1. **Planner should detect answer-format requirements**: When the task contains "Return only the X", the planner should add an explicit final step: "Call done() with ONLY the raw X value, no description."

2. **Post-processing answer extraction**: Consider adding a lightweight post-processing step that, when the task contains "Return only" language, extracts just the data value from the done() message if the model included narrative text around it. This is a safety net for when prompt instructions are insufficient.

3. **Past mistakes are being loaded but not corrected for**: The errors.jsonl shows 6 prior failures all with the same "description instead of value" pattern. The past_mistakes mechanism feeds these into context, but the model still repeats the same error. The past-mistake entries should be more specific: instead of just showing "answer is incorrect", they should say "YOUR ANSWER WAS A DESCRIPTION. The benchmark expects the RAW VALUE. You must output only: email@example.com".
