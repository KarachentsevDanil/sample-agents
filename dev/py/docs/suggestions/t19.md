# Task t19: Process inbox (invoice lookup failure)

## Failure Summary

The agent was asked to "process the inbox." The inbox contained a message from Dennis Bender (Helios Tax Group, acct_008) requesting a resend of their latest invoice. The agent correctly identified the sender, found the contact (cont_008), and determined the account (acct_008). However, it failed to locate the matching invoice files (INV-008-01.json and INV-008-02.json) and gave up with OUTCOME_NONE_CLARIFICATION. The expected outcome was OUTCOME_OK.

The invoice files INV-008-01.json and INV-008-02.json both exist and contain `"account_id": "acct_008"`. The latest is INV-008-02.json (issued 2026-08-01, total 2239). The task was fully solvable.

**Score: 0.0** (4th consecutive failure on this task across different runs)

## Root Cause Analysis

### Context Builder Phase

The context agent discovered 12 files during discovery, including all README files and the critical `docs/inbox-task-processing.md` which contains explicit instructions for invoice resend handling. The pre-loaded context was adequate -- the agent had the processing rules available.

However, the context agent did NOT pre-load any invoice files or the my-invoices/README.MD that documents the naming convention and the `account_id` linking field. This meant the agent entered the ReAct phase without understanding the invoice data model (invoices reference accounts by `account_id`, not by company name).

### Planner Phase

The planner produced a 5-step medium-complexity plan. The plan was generally correct (identify sender, find contact, find account, find invoice, send email). However, the plan did not specify HOW to find the invoice -- it did not instruct the agent to search by `account_id` field or to use the naming convention (INV-XXX maps to acct_XXX via the middle number segment).

### Primary Root Cause

**Two-hop data lookup failure.** The agent needed to follow a multi-hop reference chain:

```
inbox msg -> contact (email match) -> account_id -> invoice (account_id match)
```

The agent successfully completed hops 1-3 (email -> contact -> account) but failed at hop 4 (account -> invoice). Specifically:

1. **Wrong search strategy (step 4):** Searched invoices for "Helios Tax Group" (a human-readable name) instead of "acct_008" (the linking field). Invoices use `account_id` as the foreign key, not the company name. The agent did not understand the data model.

2. **Failed to adapt after search miss (step 8):** After the text search returned empty, the agent listed the directory and saw files named `INV-008-01.json`, `INV-008-02.json` -- but did not connect the `008` in the filename to `acct_008`. Instead, it checked only `INV-010-02.json` (the last file) based on a flawed "latest = last in directory" heuristic.

3. **Did not read the README (my-invoices/README.MD):** The README explicitly states that `account_id` links invoices to accounts and that `issued_on` determines the latest invoice. Reading this would have informed the correct search strategy.

4. **Premature give-up:** After checking just 1 of 20 invoice files and finding it didn't match, the agent gave up instead of searching by `account_id` or reading more files.

## Suggestions (generalizable)

### S1: Teach the agent to search by foreign key fields, not display names

- **What:** When a text search in a data directory returns empty, the agent should retry using the ID/foreign-key that links the entities (e.g., `account_id`) rather than human-readable names. Add a rule to the system prompt or planning prompt: "When searching structured JSON files for related records, always search by the linking ID field (e.g., account_id, contact_id), not by display names."
- **Where:** System prompt (`v13.yaml`) -- add to the SCOPE or FILE CONVENTIONS section. Alternatively, add to the planning prompt so the planner generates search-by-ID steps.
- **Why:** Structured data files use ID-based foreign keys for linking. Display names (company name, person name) are not stored in every related file. Searching by name will miss records that are only linked by ID.
- **Scope:** All tasks involving multi-hop data lookups across directories (invoices, opportunities, reminders linked to accounts/contacts).
- **Confidence:** HIGH -- this exact pattern caused the failure. The fix is simple and broadly applicable.

### S2: Add a "retry with alternative search strategy" rule when searches return empty

- **What:** Add a rule: "If a `search()` call returns zero matches but you know the data should exist, try at least one alternative search strategy before giving up. Alternatives: (a) search by ID field instead of name, (b) read the directory README for schema info, (c) inspect the naming convention of files in the directory, (d) search by a different field."
- **Where:** System prompt (`v13.yaml`) under a new SEARCH STRATEGY section, or as a tool description enhancement on the `search` tool.
- **Why:** The agent's current behavior is to give up after a single failed search. Multi-hop lookups often require adapting the search approach.
- **Scope:** All tasks where the agent searches for related records and gets empty results.
- **Confidence:** HIGH -- the agent had 3 viable fallback strategies (search by acct_008, read README, map filename pattern) but used none.

### S3: Pre-load directory READMEs into the ReAct context for data directories involved in the task

- **What:** During the context builder phase, when the task involves a specific data domain (invoices, contacts, etc.), pre-load the README from that directory so the agent understands the schema before starting the ReAct loop. The `docs/inbox-task-processing.md` references `my-invoices/` -- the context agent should follow that reference and read `my-invoices/README.MD`.
- **Where:** `agent_pipeline_openai/stages/context_agent.py` -- improve reference-following logic to also read README files in directories mentioned by the pre-loaded docs. Alternatively, add data-directory READMEs to the planning context.
- **Why:** The my-invoices/README.MD explains the `account_id` linking field and the `issued_on` date-ordering rule. Having this in context would have prevented the wrong search strategy.
- **Scope:** All tasks where the agent needs to work with structured data across multiple directories.
- **Confidence:** MEDIUM-HIGH -- the context agent already reads READMEs, but it missed this one because it wasn't directly referenced from AGENTS.md.

### S4: Improve filename-to-entity mapping awareness

- **What:** Add guidance to the system prompt or planning stage that invoice/record filenames often encode entity IDs (e.g., `INV-008-02` maps to account 008 = acct_008). When the agent sees a directory listing, it should try to correlate filename patterns with known entity IDs before opening files.
- **Where:** System prompt (`v13.yaml`) under FILE CONVENTIONS, or as a planning-stage heuristic.
- **Why:** The agent listed 20 invoice files and saw `INV-008-01.json`, `INV-008-02.json` but did not connect "008" to "acct_008". This pattern is common in CRM-style file systems.
- **Scope:** All tasks involving file lookups where filenames encode entity references.
- **Confidence:** MEDIUM -- depends on the benchmark consistently using this convention. The README-based approach (S3) is more robust.

### S5: Prevent premature OUTCOME_NONE_CLARIFICATION after insufficient search

- **What:** Add a guard rule: "Do not return OUTCOME_NONE_CLARIFICATION for missing data unless you have exhausted at least 2 different search strategies AND read the relevant directory README." This can be implemented as a validation rule or as system prompt guidance.
- **Where:** System prompt (`v13.yaml`) in the OUTCOME CODES section -- add a pre-condition for OUTCOME_NONE_CLARIFICATION. Could also be a validator rule in `infra/validator.py`.
- **Why:** The agent checked 1 of 20 invoice files and gave up. The data was there. Premature give-up is a recurring pattern (this task has failed 4 times across different runs with different failure modes).
- **Scope:** All tasks where the agent considers giving up due to "missing" data.
- **Confidence:** HIGH -- the agent gave up after minimal effort. A minimum-effort threshold before CLARIFICATION would catch this.

## Tool Recommendations

1. **Enhance `search` tool description** to hint at searching by ID fields: "Search file contents using a regex or substring pattern. For structured JSON data, search by ID fields (e.g., account_id, contact_id) rather than display names for reliable cross-entity lookups."

2. **Consider adding a `search_json` tool** (or enhancing `search`) that can filter JSON files by field value, e.g., `search_json(root="my-invoices", field="account_id", value="acct_008")`. This would make multi-hop lookups trivial and eliminate the name-vs-ID confusion entirely. However, this requires VM-side support.

## Rule Recommendations

1. **Multi-hop lookup rule:** "When resolving cross-entity references (e.g., contact -> account -> invoice), always use the ID field from the linking entity, not the display name. Read the target directory README first to learn the schema."

2. **Empty search recovery rule:** "If search() returns 0 matches and the data is expected to exist: (a) read the target directory README, (b) try searching by ID field instead of name, (c) examine filename patterns against known IDs. Do NOT give up after a single failed search."

3. **CLARIFICATION gate:** "Before returning OUTCOME_NONE_CLARIFICATION for 'missing data,' verify you have: read the directory README, tried at least 2 search strategies, and checked files whose names correlate with the target entity ID."

## Pipeline / Pre-loading Recommendations

1. **Context agent should follow data-directory references:** When `docs/inbox-task-processing.md` says "find the latest invoice for that contact's account in `my-invoices/`," the context agent should pre-load `my-invoices/README.MD` to understand the schema. Currently, only authority-chain files are discovered; data-schema files referenced from process docs are missed.

2. **Planning stage should generate ID-based search steps:** The planner has access to pre-loaded context files. When the context includes `docs/inbox-task-processing.md` (which says "find the latest invoice for that contact's account"), the planner should generate a step like "Search my-invoices/ for invoices with account_id matching the contact's account." Currently the plan is too vague about HOW to search.

3. **Past mistakes are not driving improvement:** This task has failed 4 times with different error types (no answer, FileDeleted, unexpected writes, wrong outcome). The past-mistakes injection (up to 3 mistakes shown) should lead to more cautious behavior, but the agent still took a flawed approach. Consider making the past-mistakes section more actionable: instead of just showing "expected outcome OUTCOME_OK, got OUTCOME_NONE_CLARIFICATION," include the specific failed strategy: "Previous attempt searched invoices by company name instead of account_id and gave up."
