# Task t23: Process inbox (premature clarification on disambiguable contacts)

## Failure Summary

The agent processed inbox message `msg_001`, a Discord admin message from SynapseSystems requesting: "Email [Name] asking if they want AI insights follow-up." Two contacts share the same full name -- one at Aperture AI Labs (acct_009) and one at Northstar Forecasting (acct_010). The agent found both, declared the situation ambiguous, and returned `OUTCOME_NONE_CLARIFICATION`. The expected outcome was `OUTCOME_OK`.

The disambiguation signal was present and strong: only acct_009 carries the `ai_insights_subscriber` compliance flag, and the inbox message explicitly asks about "AI insights follow-up." The accounts/README.MD even documents this flag as: "ai_insights_subscriber - VIP customer, subscribed to our Monthly AI Insights. Might need to check up on them, if they need a follow-up." The agent had all the data it needed but failed to connect the message topic to the account-level flag.

## Root Cause Analysis

### Context Builder Phase

The context agent performed well. It discovered 12 files including:
- `accounts/README.MD` (which defines the `ai_insights_subscriber` flag)
- `docs/inbox-msg-processing.md` and `docs/inbox-task-processing.md` (the process docs)
- `docs/channels/AGENTS.md` and `docs/channels/discord.txt` (channel trust)

All rule and authority files were loaded. The disambiguation rule (accounts README documenting what `ai_insights_subscriber` means) was in the preloaded context fed to both the planner and the ReAct agent. **No failure here.**

### Planner Phase

The planner created a 4-step medium-complexity plan. It correctly identified that the task involves inbox processing with channel validation. However, the plan did not include an explicit step for disambiguation strategy when duplicate names are found. The plan had no step like "if multiple contacts match by name, check account flags, roles, and message context to narrow down."

**Partial failure**: the planner missed the need for a disambiguation step despite the process docs mentioning the guardrail.

### ReAct Phase

The agent executed 13 steps:
1. Read `inbox/msg_001.txt` -- correctly identified the message
2. Read `docs/channels/AGENTS.md` -- verified channel trust framework
3. Read `docs/channels/discord.txt` -- confirmed SynapseSystems is admin
4. Searched contacts for the name -- found two matches (cont_009, cont_010)
5-6. Read both contact files -- saw different roles, accounts, emails
7-8. Read both account files -- **saw `ai_insights_subscriber` on acct_009 and the meta-note on acct_010 ("Sibling account seeded only to preserve duplicate-contact ambiguity")**
9-12. Read reminders and invoices for both (unnecessary exploration)
13. Called `done()` with `OUTCOME_NONE_CLARIFICATION`

Critical failure at step 13: The agent had read acct_009.json which contains `"compliance_flags": ["ai_insights_subscriber", ...]` and the message explicitly mentions "AI insights follow-up." The semantic match between the message topic and the account flag is direct and unambiguous. The agent also read acct_010 which literally says in its notes field "Sibling account seeded only to preserve duplicate-contact ambiguity" -- a meta-hint that this is a decoy.

The agent applied the guardrail "If multiple contacts could match, stop for clarification instead of guessing" too literally. The guardrail says "could match" -- but when contextual evidence clearly eliminates one candidate, the contacts do NOT equally match. The agent treated name-level ambiguity as final instead of attempting semantic disambiguation using available account metadata.

### Primary Root Cause

**The agent lacks a disambiguation reasoning strategy.** When duplicate names are found, it immediately invokes the clarification guardrail without first attempting to resolve the ambiguity using contextual signals from the message content cross-referenced against account/contact metadata (compliance flags, roles, account notes, industry). The guardrail was designed for truly ambiguous cases, not for cases where the message content itself provides the disambiguation key.

This is a reasoning gap in the system prompt: there is no instruction telling the agent to attempt disambiguation before invoking clarification. The guardrail is stated as absolute ("stop for clarification") without a preceding step to check whether the ambiguity can be resolved from available data.

## Suggestions (generalizable)

### S1: Add disambiguation-before-clarification instruction to system prompt

- **What**: Add a rule to the system prompt (v13) that instructs the agent: "When multiple records match by name, attempt disambiguation using contextual signals from the request (topic keywords, product references, service mentions) cross-referenced against account metadata (compliance_flags, notes, industry, role) before invoking the clarification guardrail. Only request clarification when contextual signals genuinely cannot resolve the ambiguity."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/system/v13.yaml`, in the SCOPE or a new DISAMBIGUATION section
- **Why**: The current prompt has no instruction about resolving ambiguity -- it only has the outcome code list which maps "ambiguous" directly to OUTCOME_NONE_CLARIFICATION. The agent needs explicit guidance to try disambiguation first.
- **Scope**: Affects all tasks with duplicate-name scenarios (broad, benchmark tests multiple ambiguity patterns)
- **Confidence**: HIGH -- this is the primary gap and the fix is a prompt-level instruction

### S2: Add disambiguation step to planner prompt

- **What**: Add to the planning prompt (v2) a rule: "When the task involves looking up a person or entity by name, include a plan step for disambiguation: after finding matches, cross-check message context against account/contact attributes (flags, roles, notes) to narrow candidates before acting or requesting clarification."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/planning/v2.yaml`, in the "Planning rules" section
- **Why**: The planner did not generate a disambiguation step despite the task involving a name lookup in a CRM with known duplicate-name scenarios. If the plan explicitly includes this step, the ReAct agent is more likely to follow through.
- **Scope**: All name-based lookup tasks
- **Confidence**: MEDIUM -- the planner improvement is helpful but the system prompt fix (S1) is more impactful since the ReAct agent had the data and still chose clarification

### S3: Refine the clarification guardrail interpretation in context preloading

- **What**: When `docs/inbox-task-processing.md` is preloaded and contains the "multiple contacts could match" guardrail, inject an annotation or refinement: "This guardrail applies when contacts are genuinely indistinguishable after checking all available attributes. Use message content keywords, account compliance_flags, and account notes to attempt resolution first."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts.py` (in `build_initial_user_message`) or as a post-processing annotation on trusted rule content
- **Why**: The guardrail text from the benchmark filesystem is deliberately ambiguous. The agent interprets it too conservatively. A pipeline-level annotation can soften it without modifying the benchmark data.
- **Scope**: All tasks that load inbox-task-processing guardrails
- **Confidence**: MEDIUM -- this is a targeted workaround; S1 is the more general fix

### S4: Teach the agent to use compliance_flags as semantic disambiguation keys

- **What**: Add to the system prompt or as a general reasoning rule: "Account compliance_flags and notes are semantic descriptors. When a request mentions a product, service, or feature (e.g., 'AI insights'), check if any matching account has a corresponding compliance_flag (e.g., 'ai_insights_subscriber'). A flag match is strong disambiguation evidence."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/system/v13.yaml`
- **Why**: The agent read acct_009 and saw `ai_insights_subscriber` but did not connect "AI insights follow-up" in the message to this flag. This is a reasoning pattern the model should be primed for.
- **Scope**: All tasks involving product/service-specific requests matched against account metadata
- **Confidence**: MEDIUM-HIGH -- directly addresses the specific reasoning gap in this task while being generalizable

### S5: Add a "try harder before clarification" meta-rule

- **What**: In the outcome code decision logic in the system prompt, add: "Before choosing OUTCOME_NONE_CLARIFICATION, verify you have exhausted all disambiguation strategies: (a) check if request keywords match any account flags/notes, (b) check roles for relevance to the request topic, (c) check recent activity dates, (d) check if only one candidate's account context is semantically related to the request. If any strategy yields a clear winner, proceed with OUTCOME_OK."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/system/v13.yaml`, in the OUTCOME CODES section between items 1 and 2
- **Why**: The current outcome code ordering makes OUTCOME_NONE_CLARIFICATION the second choice after security denial. The agent picks it too eagerly when any surface-level ambiguity exists. A "try harder" gate before clarification prevents premature bail-out.
- **Scope**: All tasks where the agent considers returning clarification
- **Confidence**: HIGH -- this is a general-purpose improvement that would prevent false clarification on any disambiguable scenario

## Tool Recommendations

No new tools needed. The agent's existing toolset (read_file, search) was sufficient. The agent found both contacts, read both accounts, and had all disambiguation data. The failure was in reasoning, not tooling.

## Rule Recommendations

1. **Disambiguation-first rule** (highest priority): Before invoking OUTCOME_NONE_CLARIFICATION for duplicate entity matches, the agent must attempt at least one cross-reference check between the request's semantic content and the candidate entities' metadata fields (compliance_flags, notes, role, industry).

2. **Clarification guardrail scoping rule**: The inbox-task-processing guardrail "stop for clarification instead of guessing" should be interpreted as: stop when disambiguation has been genuinely attempted and failed -- not when duplicate names are simply detected.

3. **Flag-to-topic matching rule**: When a request mentions a specific product or service keyword, the agent should search for matching compliance_flags or notes containing that keyword across candidate accounts. A match is a strong signal, not a guess.

## Pipeline / Pre-loading Recommendations

1. **Accounts README flag definitions should be surfaced prominently**: The accounts/README.MD was preloaded but contains the flag definitions at the bottom. Consider extracting compliance_flag definitions into a separate section or elevating them in the prompt assembly so the agent is more likely to reference them during disambiguation.

2. **Past-mistake injection for this pattern**: Once fixed, add a past-mistake entry for t23 that captures the lesson: "Two contacts with the same name existed but only one had the ai_insights_subscriber flag matching the request topic. The correct action was to use the flag for disambiguation, not to request clarification."

3. **Consider a disambiguation micro-stage**: For tasks that involve name lookups (detected by the planner), inject a brief reasoning prompt between finding candidates and deciding on action: "You found N candidates for [Name]. Before proceeding or requesting clarification, list each candidate's distinguishing attributes and check which one(s) match the request context." This could be a planner annotation or a ReAct-internal reasoning nudge.
