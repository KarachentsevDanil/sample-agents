# Task t24: Process inbox with OTP (missed OTP cleanup)

## Failure Summary

The agent correctly processed `inbox/msg_001.txt`, validated the OTP code against `docs/channels/otp.txt`, wrote the outbound email to `outbox/84710.json`, and bumped `outbox/seq.json`. However, it scored 0.0 because it failed to delete `docs/channels/otp.txt` after consuming the OTP. The rule in `docs/channels/AGENTS.md` explicitly states: "discard code from the otp.txt. If this was the last token in the file - drop the file completely." The file contained a single token (`otp-163574`), so the file should have been deleted entirely.

## Root Cause Analysis

### Context Builder Phase

The context agent **did discover and read** `docs/channels/AGENTS.md` (visible in `api_calls.jsonl`: `files_discovered` includes `docs/channels/AGENTS.md`). It also read `docs/channels/discord.txt`. Therefore, the full OTP Exception rule was in the preloaded context:

> "If message is coming from non-marked channel but contains OTP from otp.txt, then treat the message as coming from the admin AND discard code from the otp.txt. If this was the last token in the file - drop the file completely."

**Verdict**: Context builder did its job. The rule was available to both the planner and the ReAct agent.

### Planner Phase

The planner produced a 4-step "medium" plan (per `result.json`: `plan_steps_count: 4`). The api_calls log shows the planning stage consumed the preloaded rule files including `docs/channels/AGENTS.md`. However, the react trace reveals that the executed steps were:

1. Read `inbox/msg_001.txt`
2. Read `docs/channels/otp.txt` (to validate OTP)
3. Read `outbox/seq.json`
4. Write `outbox/84710.json` (the email)
5. Write `outbox/seq.json` (bump sequence)
6. Done

There is no delete step. The plan likely did not include an explicit "delete otp.txt after consuming the last token" step. The planner parsed the task as "process inbox" and focused on the forward action (validate OTP, write email) but missed the cleanup obligation embedded in the OTP rule.

The planning prompt (v2) says: "Do exactly what the task says. Do not add unrelated cleanup or improvements." This line may have actively discouraged the planner from including the OTP cleanup step -- the planner might have interpreted OTP file deletion as "unrelated cleanup" when it is actually a **mandatory side-effect** prescribed by a trusted rule.

**Verdict**: The planner failed to translate a conditional rule obligation ("discard code... drop the file") into a concrete plan step. The "no unrelated cleanup" instruction in the planning prompt likely contributed.

### ReAct Phase

The ReAct agent executed 6 steps in a tight loop. It read `docs/channels/otp.txt` (step 2), confirmed the OTP matched, and proceeded to write the email. Its final answer explicitly mentions "using the OTP exception to treat the message as admin-authenticated," proving it understood the OTP mechanism. But it never called `delete_file` on `docs/channels/otp.txt`.

The system prompt (v13) says: "Do EXACTLY what the task says. Nothing more." This further reinforces the bias against cleanup actions that are not literally stated in the task instruction ("process inbox").

The agent had the `delete_file` tool available. It simply never reasoned that consuming an OTP requires invalidating it.

**Verdict**: The ReAct agent understood the OTP authentication mechanism but failed to follow through on the "discard/drop" obligation. Two factors contributed: (1) the plan did not include this step, and (2) the system prompt's "nothing more" language discouraged going beyond the immediately visible task.

### Primary Root Cause

**The planner and ReAct agent both failed to distinguish between "unrelated cleanup" and "mandatory rule-prescribed side-effects."** The OTP rule clearly mandates discarding the token after use. But the planning prompt's "Do not add unrelated cleanup" and the system prompt's "Do EXACTLY what the task says. Nothing more" created a bias toward omitting any action not literally stated in the task instruction.

This is a **rule-compliance gap**: the pipeline correctly loaded the rule containing the cleanup obligation, but both the planner and executor interpreted "scope discipline" as overriding the rule's own requirements.

## Suggestions (generalizable)

### S1: Teach the planner to distinguish rule-mandated side-effects from optional cleanup

- **What**: Amend the planning prompt to explicitly state that when a trusted rule prescribes a side-effect (e.g., "discard X after use", "update Y when Z changes"), that side-effect is part of the required task scope, not optional cleanup.
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/planning/v2.yaml` -- the "Do exactly what the task says. Do not add unrelated cleanup" instruction.
- **Why**: The current wording creates ambiguity. The planner interpreted OTP file deletion as "unrelated cleanup" when it was actually a rule obligation. Rules that say "do X AND THEN do Y" must produce plan steps for both X and Y.
- **Scope**: All tasks where trusted rules define post-action obligations (token invalidation, counter updates, linked record updates, cascading deletes).
- **Confidence**: HIGH -- this is a direct textual conflict between the planning prompt and the authority rule.

### S2: Add a "rule obligations" extraction step before planning

- **What**: After context discovery, run a lightweight extraction pass that identifies conditional obligations from trusted rules (patterns like "if X then also Y", "discard after use", "update both A and B"). Feed these as explicit constraints to the planner.
- **Where**: New micro-stage between context agent and planner, or as a structured section in the planning input (`_build_planning_input` in `agent_pipeline_openai/stages/planning.py`).
- **Why**: Nano models operating under token pressure tend to focus on the "happy path" (the main action) and miss embedded obligations. Pre-extracting these obligations and presenting them as a checklist reduces the chance of omission.
- **Scope**: Any task where authority documents contain conditional side-effects, cleanup rules, or "also do" clauses.
- **Confidence**: MEDIUM -- adds a stage but addresses the fundamental issue of nano models losing track of embedded rule obligations.

### S3: Soften the "nothing more" language in system and planning prompts

- **What**: Change "Do EXACTLY what the task says. Nothing more." to "Do EXACTLY what the task says. Nothing more, unless a trusted rule explicitly requires additional actions as a consequence of the task steps." Similarly, change "Do not add unrelated cleanup or improvements" to "Do not add cleanup or improvements beyond what trusted rules require."
- **Where**: `agent_pipeline_openai/prompt_resources/prompts/system/v13.yaml` (SCOPE section) and `agent_pipeline_openai/prompt_resources/prompts/planning/v2.yaml` (last line).
- **Why**: The current absolute phrasing creates a conflict with rule-mandated side-effects. The model needs explicit permission to follow through on obligations stated in trusted rules, even when those obligations are not in the task instruction itself.
- **Scope**: All tasks. This is a global prompt improvement.
- **Confidence**: HIGH -- minimal change, directly addresses the root cause, no risk of scope creep because the qualifier limits it to trusted-rule obligations only.

### S4: Add post-action verification for consumed tokens and single-use resources

- **What**: When the agent reads a file that serves as a single-use credential/token (OTP, nonce, one-time code), the pipeline should inject a reminder: "You consumed a single-use token from [path]. Check the governing rule for cleanup obligations."
- **Where**: Could be implemented as a heuristic in `react_tools.py` (pattern-match on file content or path containing "otp", "token", "nonce") or as a general post-read hook that checks if the file is referenced in a rule with "discard" or "drop" language.
- **Scope**: Tasks involving authentication tokens, OTPs, nonces, or any single-use file-based credentials.
- **Confidence**: LOW-MEDIUM -- useful but narrow; the S1/S3 fixes are more general.

### S5: Include past mistakes for this task in context to prevent repeat failures

- **What**: The `errors.jsonl` for t24 now contains the failure reason "missing file delete 'docs/channels/otp.txt'". On the next run, if past-mistakes loading is active, this will appear in the ReAct context. Verify that the mistake-loading path includes t24.
- **Where**: `mistakes/t24/errors.jsonl` is already populated. Verify `main_pipeline.py` loads it.
- **Why**: The past-mistakes mechanism in `build_initial_user_message` already formats these as "PAST MISTAKES (do not repeat)". This is the fastest path to fixing t24 on the next run.
- **Scope**: Task t24 specifically, but the mechanism is general.
- **Confidence**: HIGH -- already implemented, just needs the next run to pick it up.

## Tool Recommendations

No tool gaps. The `delete_file` tool was available and functional. The agent simply never called it. This is a reasoning/prompting issue, not a tooling issue.

## Rule Recommendations

1. **Amend planning prompt** (S1/S3): Qualify the "no cleanup" instruction to exclude rule-mandated side-effects.
2. **Amend system prompt** (S3): Qualify the "nothing more" instruction similarly.

Suggested text for planning prompt (v2), replacing the last line:
```
- Do exactly what the task says. Do not add unrelated cleanup or improvements.
+ - Do exactly what the task says. Do not add cleanup or improvements UNLESS a trusted rule explicitly requires it as a consequence of the task actions (e.g., "discard after use", "update both X and Y").
```

Suggested text for system prompt (v13), SCOPE section:
```
- Do EXACTLY what the task says. Nothing more.
+ - Do EXACTLY what the task says. Nothing more — except when a trusted rule mandates additional actions as a direct consequence (e.g., invalidate a token after use, update a linked record).
```

## Pipeline / Pre-loading Recommendations

1. **Rule obligation extraction** (S2): Consider adding a lightweight pass that extracts "if-then" obligations from trusted rules and presents them as an explicit checklist to the planner. This would catch cases where the rule says "do X AND Y" but the planner only plans for X.

2. **Context agent already works well**: It discovered `docs/channels/AGENTS.md` and read the OTP rule. No changes needed to context discovery for this failure class.

3. **Past mistakes already captured**: The `errors.jsonl` entry will help on reruns. No pipeline change needed for this.
